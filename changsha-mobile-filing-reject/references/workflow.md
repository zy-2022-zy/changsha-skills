## 生产门户实测结论（2026-11-05）

文档方法一写的入口“端口上报管理 → 端口信息报送 → 真实端口数据管理”，配合“状态 = 集团驳回”，在当前门户查不出任何记录：不限状态、不限日期、限定“接入地市 = 长沙”均为 0 条，与页面顶部统计卡（待审批 31 条、审批通过 53,584 条）自相矛盾。筛选结果为空时点击“批量导出”，门户对空结果集导出直接返回 `{"msg":"操作异常,请联系系统管理员","code":500}`，这正是此前多次失败的直接原因。

真正有集团驳回数据的入口是“端口上报管理 → 驳回端口查询”：

- 表格列为 端口 / 端口类型 / 驳回类型 / 驳回原因 / 端口提交人 / 驳回时间 / 操作，筛选条件为“驳回时间”范围。
- 该页导出调用 `POST /ismsports/api/portal-api/rejectPort/submitExportTask`，正常返回批次号，任务名称为“驳回端口导出”，数据类别“驳回端口”。
- 该页“批量导出”不筛状态，默认导出的就是集团驳回记录，无需再选状态。

下载同样与旧流程不同：批次行的“下载”会打开“文件列表”弹窗（`/ismsports/api/portal-api/taskExportedFile/pageList`），里面是按万分片生成的多个 xlsx，需要逐个下载后合并。真实下载接口是 `/ismsports/api/file-api/exportFile/downloadFileByFileId?fileId=...`（不是旧报备工具用的 `downloadFile`），首次请求可能返回 JSON 错误体，需要等后续返回 PK 头的那一次。每个分片都带自己的表头，合并时只保留第一份，否则行数会多出分片数。

实测批次 `2118179097720991746`：门户“数据总量 / 已导数量”均为 107284，合并下载后统计也是 107284 行，表头仅 1 行，端口号无重复。

## 分片文件尾部多余字节（2026-11-05 实测）

批次 `2118192243965767681`（数据总量 108232，共 11 个分片）中，第 8 个分片下载后无法解析，报 `Unsupported ZIP Compression method NaN`。

逐字节分析该分片（202752 字节）：

- 文件开头是正常的 ZIP 本地文件头签名 `504b0304`。
- 扫描发现两个 EOCD 候选：偏移 201711 和 202735。
- 偏移 201711 的 EOCD 完全自洽：条目数 9，中央目录偏移 201136，中央目录大小 575，期望文件长度 201733，落在文件范围内；中央目录起始签名是合法的 `504b0102`，9 个条目（`[Content_Types].xml`、`_rels/.rels`、`docProps/app.xml`、`docProps/core.xml`、`xl/sharedStrings.xml`、`xl/styles.xml`、`xl/workbook.xml`、`xl/_rels/workbook.xml.rels`、`xl/worksheets/sheet1.xml`）的 `localOffset` 也都指向文件内的合法位置。
- 偏移 202735 的 EOCD 只有 17 字节（标准要求至少 22 字节），是这段 1019 字节多余数据里的伪造记录。

结论：服务端在有效 ZIP 之后追加了约 1KB 垃圾数据，并在尾部放了一个不完整的 EOCD。解析器按"最后一个 EOCD"读取就会定位到垃圾数据里而失败。按第一个自洽 EOCD 截断到 201733 字节后，文件正常解析出 10007 行（1 行表头 + 10006 条数据），与门户数据总量吻合：其余 10 个分片合计 98226 行，加上本分片 10006 行，正好 108232。

实现：`src/workbook.ts` 的 `zipEndOffset` 从前往后找中央目录偏移能对上的 EOCD，`repairXlsx` 按该位置截断。下载、合并、计数三处都走修复逻辑，因此单个分片异常不会作废整批数据。注意：不能只判断"末尾有没有 EOCD"，必须验证中央目录偏移落在文件内且签名正确。

## 复用与边界

- 参考实现：同仓库 `code/changsha-mobile-filing-automation`，复用了 `.env` 解析、完整批次号字符串匹配、运行锁的实现，并借鉴人工登录、会话保存、Element UI 固定操作列和批量导出查询模式。
- 本目录独立安装运行，不引用旧程序的源码、生产 `.env`、会话、下载数据或日志，不修改旧 skill。
- 本流程导出集团驳回记录；文档方法一所述“真实端口数据管理 + 状态 = 集团驳回”在当前门户已查不出数据，实际改用“驳回端口查询”（详见上文实测结论）。“导入失败数据”任务不属于本流程。
- 已连接生产门户验证（2026-11-05，批次 `2118179097720991746`，107284 条）。门户若改动入口或下载方式，需要调整 `src/portal.ts`，并优先用“驳回端口查询”核对实际数据。
- 文件计数规则适用于单张业务表、表头之后均为业务行的下载文件；遇到汇总尾行、多业务表或表头异常应先核查再调整解析器，不能声称已得到准确数量。

## SEDP 上传格式转换

门户导出的“驳回端口”文件表头为 `端口 / 端口类型 / 驳回类型 / 驳回原因`，其中“端口”列混有真实端口和局数据端口（2026-11-04 批次为 107274 + 10）。SEDP 的“子端口”列两者都要，因此逐行原样带出，不按“端口类型”筛选或拆分。

集团驳回记录再次上传报备必然失败，所以“报备结果”列固定写“失败”，“备注”列按要求统一写“集团驳回”（不沿用门户的驳回原因原文），“签名”列按要求留空。

转换有两条硬性约束：驳回类型必须全部是“集团驳回”，端口号必须是纯数字。任一条不满足就整体停止并报错，不静默跳过行——静默跳过会让 SEDP 数量和门户数据总量对不上，人工复核时反而更难发现。

实测批次 `2118179097720991746` 转换结果：107284 行，其中真实端口 107274、局数据端口 10；签名列全空，报备结果全部“失败”，备注全部“集团驳回”。SEDP 转换失败不丢弃已下载的驳回结果，原因记入状态的 `sedpError`，可用 `pnpm start -- sedp --file <已下载.xlsx>` 单独重试。
